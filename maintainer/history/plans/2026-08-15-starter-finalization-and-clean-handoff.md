# План P0: финализация и безопасная очистка Codex Starter

**Дата:** 2026-08-15
**Автор:** Арсений + Codex
**Приоритет:** P0 - начать первым
**Статус:** завершён и принят 2026-08-16
**Зависимости:** нет

## Цель

Сделать однозначный и безопасный конец Starter: после всех обязательных ответов Codex сам запускает проверку, показывает будущую очистку, получает подтверждение, удаляет только свою служебную оболочку и проверяет уже чистый проект.

## Результат простыми словами

Пользователь проходит такой путь:

`привет -> вопросы -> проверка -> показ изменений -> подтверждение -> очистка -> повторная проверка -> первая рабочая задача`

После этого:

- Starter больше не предлагает онбординг;
- в проекте нет служебных файлов шаблона;
- полезный контекст и пользовательские файлы сохранены;
- новое окно Codex сразу понимает настоящий проект;
- пользователь видит ясное сообщение о полном завершении.

## Почему это P0

Без этого Starter нельзя честно назвать законченным. Он может собрать часть контекста, но не доказывает готовность, не имеет явного конца и оставляет внутри пользовательского проекта собственную оболочку.

Этот план важнее публикации, релиза и визуальной полировки. Сначала механизм должен правильно завершать свою основную работу и ничего не ломать.

## Что входит

- определение момента, когда обязательные вопросы закончились;
- единый конец для AUTOPILOT и выбранного пользователем результата POST_AUTOPILOT;
- финальная проверка до очистки;
- устранение противоречий в активных правилах;
- честная проверка реально подключённой защиты;
- создание финальных документов настоящего проекта;
- предварительный просмотр очистки;
- явное подтверждение пользователя;
- удаление только заранее известных файлов Starter;
- повторная проверка после очистки;
- проверка нового окна Codex;
- восстановление после прерванной финализации.

## Что не входит

- GitHub Template и публичная упаковка;
- тег, GitHub Release, commit или push;
- автоматическое изменение Git remote;
- plugins, MCP, browser, automations и другие расширения;
- разработка первой функции продукта пользователя;
- увеличение количества папок и обязательных документов.

Эти задачи относятся к P1, P2 или к будущему проекту пользователя.

## Обязательные решения

До реализации считаются принятыми следующие правила:

1. Пользователь не вводит специальную команду завершения.
2. Последний ответ завершает интервью, но ещё не завершает Starter.
3. Starter считается завершённым только после повторной проверки очищенного проекта.
4. POST_AUTOPILOT можно пройти или явно пропустить. Оба пути должны иметь один общий финал.
5. Неизвестные файлы всегда сохраняются.
6. Удаление выполняется только по точному списку разрешённых путей.
7. Перед удалением пользователь видит полный список изменений и подтверждает его.
8. `AGENTS.md`, `PROJECT_STATE.md`, `README.md` и `STRUCTURE.md` сначала переписываются под настоящий проект и только затем удаляется оболочка Starter.
9. Отдельный постоянный файл `starter-completed` не создаётся.
10. Commit, push и изменение remote не выполняются автоматически.

## Состояния процесса

Нужен один понятный маршрут состояний:

1. `interview` - Codex задаёт только нужные вопросы.
2. `final_validation` - проверяет собранный контекст.
3. `cleanup_preview` - показывает, что останется, изменится и удалится.
4. `cleanup_confirmed` - пользователь подтвердил точный список.
5. `cleanup_running` - выполняется безопасная очистка.
6. `post_cleanup_validation` - проверяется уже чистый проект.
7. `completed` - результат подтверждён, временное состояние Starter можно удалить.

Если окно закрыто на любом этапе, следующее окно должно продолжить с последнего безопасного состояния, а не начинать всё заново.

## Состояния ответов

Каждый обязательный вопрос получает одно состояние:

- `answered` - ответ получен;
- `unknown_for_now` - ответ пока неизвестен, но это не мешает начать работу;
- `not_applicable` - вопрос не относится к этому проекту.

Блокировать завершение можно только тогда, когда без ответа нельзя безопасно или осмысленно начать проект. Например, неизвестно, что создаётся, для кого, какой ближайший результат нужен или как хранить приватные данные.

## Категории файлов при очистке

Перед написанием механизма нужно сверить актуальное дерево репозитория и положить каждый известный путь ровно в одну категорию.

### Оставить

- финальные файлы настоящего проекта;
- заполненный `business/`;
- пользовательский исходный код;
- нужные и заполненные `ai-clone/` и `mastery/`;
- реальные проектные skills;
- `plans/` и `retrospectives/` с их рабочими шаблонами;
- подтверждённые настройки Git и защитные механизмы проекта.

### Переписать под проект

- `AGENTS.md`;
- `PROJECT_STATE.md`;
- `README.md`;
- `STRUCTURE.md`.

### Удалить как Starter

- `AUTOPILOT.md`;
- `POST_AUTOPILOT.md` после прохождения или явного пропуска;
- `autopilot/`;
- состояние онбординга и временное состояние финализации;
- `maintainer/`;
- учебные примеры и starter-only templates;
- документы миграции и обслуживания шаблона;
- setup-промпты и проверки, которые нужны только автору Starter;
- планы и история разработки самого Starter в пользовательской копии;
- внутренний помощник очистки и его манифест после успешной финальной проверки.

### Решить по фактическому использованию

- пустые `ai-clone/` и `mastery/`;
- `prompts/`;
- `experiments/`;
- `.agents/skills/`;
- safety scripts, которые могут быть полезны уже настоящему проекту;
- starter-specific документы качества и устранения проблем.

Главное правило: путь, которого нет в проверенном манифесте, удалять нельзя.
