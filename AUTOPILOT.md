# AUTOPILOT - онбординг Codex Starter

> Это файл для Codex. Если ты пользователь и читаешь это вручную: открой проект в Codex и напиши любую фразу. Codex сам продолжит с нужного шага.

## Правила для Codex

1. Иди по шагам 1-10 и обновляй `last_completed_step` после каждого шага.
2. Если сессия прервалась, прочитай `last_completed_step` и продолжи со следующего шага.
3. Не включай рискованные режимы без подтверждений пользователя.
4. Перед shell-командами объясняй, зачем они нужны.
5. Говори коротко: пользователь учится, ему нужна ясность, а не лекция.
6. Не коммить `.business/` после заполнения реальными данными.

## Режимы работы

- **Онбординг:** если `completed: false` и пользователь готов настраивать проект, выполняй шаги 1-10 и меняй файлы.
- **Аудит:** если пользователь просит “проанализировать”, “оценить”, “найти улучшения” или “разобрать прохождение AUTOPILOT”, только читай файлы и дай список улучшений. Не редактируй и не коммить.
- **Правка шаблона:** меняй `AUTOPILOT.md`, `templates/`, `plans/`, `retrospectives/` только после прямой просьбы внести изменения. Делай это отдельной веткой и отдельным коммитом.
- **Завершённый AUTOPILOT:** если `completed: true`, не продолжай шаги заново, пока пользователь явно не попросит повторный онбординг.

### Узкий путь

Подходит для:

- лендинга, сайта-визитки, маленького MVP, учебного проекта;
- проекта без сложной экономики, сегментов, воронки и долгой продуктовой стратегии;

- суть проекта;
- для кого проект;

- главную цель;

- `.business/INDEX.md`;
- `.business/project.md`;
- `.business/product.md`;
- `.business/audience.md`;
- `.business/goals.md`;
- `.business/constraints.md`;
- `.business/brand.md`, если есть UX/тексты/визуальный стиль.

На что влияет:

- Codex быстрее понимает проект;
- меньше файлов и меньше токенов на будущих задачах;
- меньше риск создать библиотеку, которую никто не будет читать.

Подходит для:

- коммерческого продукта, SaaS, маркетплейса, сложного сервиса, долгой разработки;
- проекта с несколькими сегментами аудитории, монетизацией, воронкой, конкурентами, KPI;
- ситуации, где Codex будет помогать не только с кодом, но и с продуктом, UX, маркетингом и приоритизацией.

Что обсуждаем:

- компанию/контекст;
- продукт и варианты развития;
- сегменты аудитории, путь клиента и возражения;
- цели и метрики;
- экономику;
- маркетинг, конкурентов и воронку;

## Шаг 8. Интервью и заполнение `.business/`

Иди по выбранной глубине.

### Если выбран узкий путь

Задавай вопросы блоками, по 2-4 вопроса на блок:

1. `project.md` - название, суть, зачем проект нужен, кто принимает решения.
2. `product.md` - что создаём, главный сценарий, MVP, что точно не входит.
3. `audience.md` - кто пользователь, какая боль, что он должен понять или сделать.
4. `goals.md` - ближайшая цель, критерий успеха, что важно проверить первым.
5. `constraints.md` - стек, бюджет, сроки, риски, ограничения по данным и безопасности.
6. `brand.md` - тон, визуальные ориентиры, стиль интерфейса и текстов, если это важно для проекта.

После блока `product.md` сделай Reality Check: 2-3 риска идеи и спроси, продолжаем ли.

В конце сгенерируй `.business/INDEX.md`: краткое описание проекта, список созданных файлов и правило «читать только нужный контекст».

### Если выбран расширенный путь

Иди блоками, по 3-5 вопросов на блок:

1. `company/` - название, суть проекта, команда, юр. контекст, ценности.
2. `products/` - что продаём/строим, стадии, доступ/цены.
3. `audience/` - пользователь, боль, возражения, путь.
4. `goals/` - год, квартал, месяц, KPI.
5. `economics/` - доходы, расходы, unit economics или costs-only для некоммерческого проекта.
6. `marketing/` - каналы, воронка, конкуренты, контент.
7. `assets/` - бренд, тон, отзывы, материалы.

После блока `products/` сделай Reality Check: 2-3 риска идеи и спроси, продолжаем ли.

В конце сгенерируй `.business/INDEX.md`: краткое описание проекта, список файлов, правило «читать только нужный контекст».

После каждого блока записывай только нужные файлы и обновляй `last_completed_step: 8.N`.

Перед созданием каждого файла проверь:

- какую будущую задачу он ускорит;
- когда Codex должен его читать;
- нельзя ли этот контекст оставить в уже существующем файле.

Обнови `last_completed_step: 8`.

Проверка рабочего цикла без учебного мусора:

1. Покажи пользователю, где лежат `plans/TEMPLATE.md` и `retrospectives/TEMPLATE.md`.
2. Коротко объясни цикл `plan → implement → verify → retro`.
3. Не создавай `HELLO.md`, hello-план и hello-ретро по умолчанию.
4. Если пользователь хочет живую демонстрацию, создай её только в `examples/hello-cycle/`, а не в корне проекта.
5. Для реальной следующей задачи создай настоящий план с названием этой задачи.

Почему: учебные файлы полезны для демонстрации, но в реальном проекте они быстро превращаются в шум. В `plans/` и `retrospectives/` должны попадать реальные задачи и заметные сессии.
