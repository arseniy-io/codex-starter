# AGENTS.md - правила работы Codex в этом проекте

> **СТОП. Читается первым в каждой новой сессии Codex.**
>
> Перед началом работы проверь:
> 1. Есть ли файл `AUTOPILOT.md` в корне проекта.
> 2. Если да - открой его и проверь поле `completed:` в начале файла.
> 3. Если `completed: false` - начни онбординг фразой:
>
> > «Вижу, что ты открыл Codex Starter. Давай настроим проект. Это займёт 60-90 минут, можно разбить на 2 сессии. Готов начать?»
>
> Если пользователь согласился - читай `AUTOPILOT.md` целиком и следуй шагам.
> Если `completed: true` или `AUTOPILOT.md` отсутствует - работай по правилам ниже.
> Если пользователь явно обслуживает сам starter-template, а не проходит онбординг проекта, не запускай AUTOPILOT и работай по задаче пользователя.
> Если пользователь просит только аудит или список улучшений для starter-template, не редактируй файлы до отдельной прямой просьбы.

## Ключевые принципы работы

1. **Сначала контекст, потом действие.** Для бизнес-текстов, UX, логики продукта и приоритизации читай `.business/INDEX.md` и только нужные файлы из `.business/`.
2. **Одна сессия - одна задача.** Если задача расползается, предложи вынести часть в отдельную сессию или план.
3. **Перед новым промптом проверь `prompts/INDEX.md`.** Если там уже есть подходящий workflow, используй его.
4. **Для новой функции создай план** в `plans/YYYY-MM-DD-название.md`: фазы, статусы `[ ]/[x]`, проверки, итог.
5. **После заметной работы создай ретро** в `retrospectives/YYYY-MM-DD_HH-MM_название.md`: задача, что сделал, результат, что улучшить, следующий шаг.
6. **Перед push запусти проверки стека.** Минимум: форматирование/линтер/тесты/сборка, если они есть в проекте.
7. **Не трогай чужие изменения.** Не используй `git add .` в обычной работе; стейджь только свои файлы.
8. **Данные, которые часто меняются, держи в БД/конфиге**, а не хардкодь в коде.

## Безопасность

- Не проси и не сохраняй паспорта, пароли, ПДн клиентов, приватные ключи, seed-фразы и реальные API-ключи.
- Не читай `.env` целиком. Если нужна переменная, проси пользователя назвать её или читай только конкретную строку вида `VAR_NAME=`.
- Перед рискованными командами объясняй, что меняется и как откатить.
- Перед удалением, перемещением или массовой перезаписью файлов проверь путь и границы workspace.
- Перед установкой skills, plugins, MCP servers или пакетов из интернета проведи аудит источника и объясни риск.
- Project-level guardrails лежат в `.codex/` и `.codex/hooks/`.

## Триггеры операционного планирования

| Фраза пользователя | Действие |
|---|---|
| «давай спланируем неделю» / «план на неделю» | Прочитай `.business/goals/monthly.md`, создай `.business/execution/YYYY-WNN.md` с задачами по дням. |
| «добавь задачу» / «запиши задачу» | Если есть дата - добавь в файл недели. Без даты - в `.business/execution/backlog.md`. |
| «что на этой неделе?» | Покажи файл текущей ISO-недели. |
| «итоги недели» / «закрой неделю» | Заполни секцию «Итог недели». |
| «перенеси X на следующую неделю» | Убери из текущей недели, добавь в следующую. |
