# AGENTS.md - правила работы Codex в этом проекте

> **СТОП. Читается первым в каждой новой сессии Codex.**
>
> Если пользователь обслуживает сам starter-template, не запускай пользовательский AUTOPILOT и переходи к правилам ниже.
>
> В обычной пользовательской копии перед началом работы проверь `AUTOPILOT.md` и `.codex/autopilot-state.yml`:
> 1. Если файлов нет - Starter уже удалён, работай как с обычным проектом.
> 2. Если `finalization.current_stage: interview` и `autopilot.interview_completed: false` - продолжи `AUTOPILOT.md` с сохранённого шага.
> 3. Если `autopilot.interview_completed: true`, `post_autopilot.decision: running` и `post_autopilot.completed: false` - продолжи `POST_AUTOPILOT.md`.
> 4. Если `finalization.current_stage` равен `final_validation`, `cleanup_preview`, `cleanup_confirmed`, `cleanup_running` или `post_cleanup_validation` - не начинай интервью заново. Открой раздел `Единая финализация` в `AUTOPILOT.md` и продолжи с последней безопасной точки.
> 5. Только если `autopilot.interview_completed: false` и пользователь ещё не согласился на настройку, начни фразой:
>
> > «Вижу, что ты открыл Codex Starter. Давай настроим проект. Это займёт 60-90 минут, можно разбить на 2 сессии. Готов начать?»
>
> `autopilot.completed: true` разрешён только после проверки уже очищенного проекта. Последний ответ интервью сам по себе не означает завершение.
> Если пользователь просит только аудит или список улучшений для starter-template, не редактируй файлы до отдельной прямой просьбы.

## Что это за проект

**Codex Starter** - шаблон и методология для проектов, где Codex должен быстро понимать контекст, не читать лишние файлы и сразу переходить к рабочей задаче.

Короткий текущий вход для обслуживания самого starter - `PROJECT_STATE.md`.
Финальные правила, которые AUTOPILOT генерирует для пользовательского проекта, живут в `templates/AGENTS.md.tmpl`.
Подробная карта папок - `STRUCTURE.md`.

## Маршрут работы

1. В начале новой сессии после этого файла прочитай `PROJECT_STATE.md`.
2. Если задача про обычный пользовательский онбординг - работай по `AUTOPILOT.md` и обновляй `.codex/autopilot-state.yml`.
3. Если задача про второй этап настройки - работай по `POST_AUTOPILOT.md` и обновляй `.codex/autopilot-state.yml`.
4. Если задача про обслуживание самого starter-template - используй текущий план в `plans/`, навигацию из `PROJECT_STATE.md` и историю из `maintainer/` только при прямой необходимости.
5. Если пользователь просит только аудит или список улучшений - не редактируй файлы до отдельной прямой просьбы.
6. Перед новым промптом проверь `prompts/INDEX.md`.

Правило контекста: сначала короткий вход, затем индекс нужной зоны, затем только 1-3 релевантных файла. Не читай всю `business/`, `ai-clone/`, `mastery/`, `maintainer/`, все планы или все ретро без явной причины.

## Работа с изменениями

- Перед заметной правкой starter создай или обнови план в `plans/`.
- После каждой фазы обновляй план: что сделано, какие проверки прошли, какой вывод.
- Для истории разработки самого starter используй `maintainer/history/`, чтобы `plans/`, `retrospectives/`, `experiments/` оставались чистыми рабочими папками.
- Не трогай чужие изменения и не используй `git add .` в обычной работе.
- Перед push или публикацией запускай релевантные проверки: `scripts/security-audit.ps1`, `scripts/user-project-safety-check.ps1`, hook smoke-test, markdown-ссылки, `git diff --check`.

## Безопасность

- Не читай `.env` целиком и не сохраняй реальные секреты в репозитории.
- Перед удалением, массовым перемещением или перезаписью файлов проверь путь.
- Перед установкой skills, plugins, MCP servers или пакетов из интернета проведи аудит источника.
- Если действие рискованное, объясни риск и дождись явного направления пользователя.
- Если `ai-clone/` заполнен реальными личными данными, перед commit проверь, должен ли он быть приватным или снятым с tracking.
