# AGENTS.md - правила работы Codex в этом проекте

> **СТОП. Читается первым в каждой новой сессии Codex.**
>
> Перед началом работы проверь:
> 1. Есть ли файл `AUTOPILOT.md` в корне проекта.
> 2. Если да - открой его и проверь поле `completed:` в начале файла.
> 3. Если `completed: false` - начни онбординг фразой:
>
> > «Вижу, что ты открыл Codex Starter. Давай настроим проект. Это займёт 60-90 минут, можно разбить на 2 сессии. Готов начать?»
>
> Если пользователь согласился - читай `AUTOPILOT.md` целиком и следуй шагам.
> Если `completed: true`, проверь `POST_AUTOPILOT.md`: если там `completed: false`, предложи второй этап настройки.
> Если `POST_AUTOPILOT.md` тоже завершён или отсутствует - работай по правилам ниже.
> Если пользователь явно обслуживает сам starter-template, а не проходит онбординг проекта, не запускай AUTOPILOT и работай по задаче пользователя.
> Если пользователь просит только аудит или список улучшений для starter-template, не редактируй файлы до отдельной прямой просьбы.

---

## Что это за проект

**Codex Starter** - шаблон и методология для проектов, где Codex должен быстро понимать контекст, не читать лишние файлы и сразу переходить к рабочей задаче.

Короткий текущий вход для обслуживания самого starter - `PROJECT_STATE.md`.
Подробный контекст проекта после онбординга - `.business/INDEX.md`, если папка заполнена.
Личный контекст автора - `ai-clone/INDEX.md`, если пройден `POST_AUTOPILOT.md`.
Методологии и экспертные подходы - `mastery/INDEX.md`, если пройден `POST_AUTOPILOT.md`.

## Структура репозитория

```
./
├── AGENTS.md                ← этот файл, durable-инструкции для Codex
├── PROJECT_STATE.md         ← короткий вход для текущего состояния
├── AUTOPILOT.md             ← сценарий первого онбординга
├── POST_AUTOPILOT.md        ← второй этап настройки
├── TROUBLESHOOTING.md       ← решения типовых проблем Codex
├── .codex/                  ← project config, hooks и локальные настройки Codex
├── .agents/skills/          ← локальные repo-skills
├── ai-clone/                ← личный контекст автора решений
├── mastery/                 ← методологии и экспертные подходы
├── .business/               ← бизнес-контекст проекта после онбординга
├── plans/                   ← технические планы
├── retrospectives/          ← короткая память после сессий
├── experiments/             ← stress-test, гипотезы и проверочные прогоны
├── prompts/                 ← библиотека готовых промптов
└── templates/               ← шаблоны для генерации файлов
```

## Как работать

1. В начале новой сессии после `AGENTS.md` прочитай `PROJECT_STATE.md`, если он есть.
2. Для бизнес-задач, UX, текстов и продуктовых решений сначала читай `.business/INDEX.md`, затем только нужные файлы из `.business/`.
3. Для задач про тон, стиль, личные предпочтения и устойчивые ошибки читай `ai-clone/INDEX.md`, затем 1-3 нужных файла из `ai-clone/`.
4. Для задач, где нужен экспертный метод или фреймворк, читай `mastery/INDEX.md`, затем нужную область из `mastery/`.
5. Перед заметной новой функцией создай план в `plans/YYYY-MM-DD-название.md`. Для микрозадач без риска достаточно краткого итога в ответе.
6. После реализации обнови план, если он был создан: что сделано, что осталось, какие проверки прошли.
7. После заметной сессии обнови `PROJECT_STATE.md`, если изменился фокус, следующий шаг или список ключевых файлов.
8. После заметной сессии создай ретро в `retrospectives/YYYY-MM-DD_HH-MM_название.md`. Для коротких правок ретро не обязательно.
9. Перед закрытием заметной фичи сделай лёгкий review-cycle: ошибки, edge cases, реальность проблемы, security.
10. Перед push запусти проверки стека: линтер, тесты, сборку или локальный smoke test.
11. Не трогай чужие изменения и не используй `git add .` в обычной работе.
12. Перед новым промптом проверь `prompts/INDEX.md`.

## Маршрутизация контекста

- Текущий статус, фокус и следующий шаг - `PROJECT_STATE.md`.
- Бизнес, продукт, UX, аудитория, цены, экономика - `.business/INDEX.md`.
- Голос, стиль, личные предпочтения, способ мышления, повторяющиеся ошибки - `ai-clone/INDEX.md`.
- Экспертный метод, фреймворк, discovery, анализ через подход - `mastery/INDEX.md`.
- Реализация заметной фичи - актуальный план в `plans/`.
- Опыт прошлых сессий и выводы после работы - `retrospectives/`.
- Stress-test, гипотезы и проверочные прогоны - `experiments/`.

Правило: сначала короткий вход, затем индекс нужной зоны, затем только 1-3 релевантных файла. Не читай всю `.business/`, `ai-clone/` или `mastery/` без явной причины.

## Масштаб проекта

- `lite` - лендинг, портфолио, локальная услуга, маленький сайт. Обычно достаточно `PROJECT_STATE.md`, `.business/INDEX.md` и 3-5 коротких `.business`-файлов. Не заполняй `ai-clone/` или `mastery/` без прямой задачи про стиль, голос, предпочтения или методологию.
- `standard` - продукт средней сложности: каталог, запись, простая админка, контентный продукт. Обычно достаточно 6-10 рабочих файлов. Не создавай роли, security, integrations, roadmap и execution без явного deep-триггера.
- `deep` - SaaS, marketplace, AI-продукт, платежи, роли, интеграции, пользовательские данные, security. Deep не равен большой библиотеке: держи `MVP vs later` и короткую карту scope/data/roles/integrations/trust.

Маленький проект не должен становиться большой библиотекой. Большой проект не должен оставаться без карт рисков, данных, ролей и интеграций.

## Review-Cycle

Для заметных фич перед завершением проверь:

- реальные ошибки в diff;
- edge cases;
- соответствует ли решение реальной проблеме проекта;
- понятен ли код свежим взглядом;
- security, если есть данные пользователей, внешние API, платежи, файлы или отправка данных наружу.

Для микрозадач и небольших текстовых правок полный review-cycle не нужен.

## Skills, Plugins, MCP

- Skill - reusable workflow с `SKILL.md`.
- Plugin - устанавливаемый bundle, который может включать skills, apps, MCP и hooks.
- MCP - подключение к внешнему сервису или локальному серверу инструментов.

Ничего не устанавливай "на всякий случай". Если workflow нужен только этому репозиторию, предпочитай repo-skill в `.agents/skills/`. Перед внешними skills/plugins/MCP проверяй источник, README, scripts/hooks, доступ к `.env`, внешние URL, удаление файлов и какие данные уходят наружу.

## Browser И Automations

- In-app browser используй для localhost, публичных страниц и визуальной проверки.
- Chrome extension нужен только когда требуется залогиненный Chrome или внутренние панели.
- Automation нужна для повторяющихся задач по расписанию или heartbeat текущего thread.

Не подключай Chrome и не создавай automation без реальной нужды. Для file-changing automation предпочитай безопасный режим: отдельный worktree или явное согласие на local mode.

## Безопасность

- Не читай `.env` целиком и не сохраняй реальные секреты в репозитории.
- Перед удалением, массовым перемещением или перезаписью файлов проверь путь.
- Перед установкой skills, plugins, MCP servers или пакетов из интернета проведи аудит источника.
- Если действие рискованное, объясни риск и дождись явного направления пользователя.
- Если `ai-clone/` заполнен реальными личными данными, перед commit проверь, должен ли он быть приватным или снятым с tracking.
