# plans/ - технические планы реализации

## Правила

1. **Один план = одна функция.** Не «сделать проект», а «добавить форму оплаты».
2. **Имя файла:** `YYYY-MM-DD-название-функции.md`
3. **План делится на фазы.** У каждой фазы статус `[ ]` или `[x]`.
4. **В конце плана** - итоговый блок: реализован целиком или нет, что осталось.
5. **План нужно актуализировать** после заметной сессии: отмечать сделанное, дописывать что изменилось.

Здесь должны лежать только `README.md`, `TEMPLATE.md` и планы реальной текущей работы. Закрытые планы сохраняй как историю решений, но не считай их активными.

## Когда план нужен

- Нужен: новая функция, заметный UX/архитектурный шаг, рискованное изменение, работа дольше одной короткой сессии.
- Не обязателен: анализ без правок, текстовая правка, мелкий фикс до 15-20 минут, проверка статуса.
- Если микрозадача разрослась - создай план по ходу и продолжай по нему.

## Зачем это нужно

Новый чат Codex не помнит, что было сделано в предыдущем. **План - помнит.** Когда открываешь новый чат для продолжения задачи, Codex читает план, видит где остановились, что сделано, что нет - и продолжает оттуда.

Без плана большие задачи разваливаются на 3-й день работы.

## Как работать с планом

1. **Создай** план в начале задачи: `plans/2026-04-23-payment-form.md` по шаблону `TEMPLATE.md`.
2. **Проверь** риски, пропущенные случаи и критерии готовности. Если в проекте сохранена библиотека workflow-промптов, можно использовать подходящий сценарий оттуда.
3. **Реализуй** по фазам. После каждой фазы - ставь `[x]`.
4. **В конце** закрой блок «Итог» - что получилось, что не сделано, что осталось на потом.

Если нужно выбрать один план для анализа: бери явно указанный пользователем; если его нет - связанный с текущей задачей; если связи нет - самый свежий содержательный план.
