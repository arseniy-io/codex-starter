# Сравнение: волна 3 - тяжёлые проекты

Дата: 2026-06-19

## Что проверяли

Три тяжёлых проекта:

- B2B SaaS для обработки заявок;
- marketplace услуг;
- AI CRM / AI-консультант для продаж.

Цель проверки: понять, включает ли AUTOPILOT `deep` только по настоящим deep-триггерам и может ли держать тяжёлый проект компактным.

## Результаты по проектам

### 1. B2B SaaS для обработки заявок

Оценка агента: 9/10.

Настоящие deep-триггеры:

- роли и права;
- клиентские данные;
- вложения;
- экспорт;
- API/webhooks;
- SLA;
- audit/security.

Что сработало:

- `deep` выбран по делу;
- risk/trust слой был нужен, а не добавлен "для красоты";
- новый Codex может войти через `AGENTS.md` + `PROJECT_STATE.md`;
- агент удержал MVP и не строил весь enterprise-мир сразу.

Главный риск: следующий Codex может начать расширять `deep` слишком быстро, если MVP не держать жёстко.

### 2. Marketplace услуг

Оценка агента: 9/10.

Настоящие deep-триггеры:

- две стороны сделки;
- платежи и выплаты;
- споры;
- отзывы;
- модерация;
- антифрод;
- trust/safety.

Что сработало:

- AUTOPILOT не перепутал marketplace с каталогом услуг;
- деньги, доверие и споры стали частью ядра продукта;
- deep помог собрать MVP без бесконечной энциклопедии;
- отчёты остались UTF-8 и читаются нормально.

Главный риск: marketplace легко раздувается в legal, roadmap, forecast, unit economics и security-справочник раньше, чем понятна первая сделка.

### 3. AI CRM / AI-консультант для продаж

Оценка агента: 8.5/10.

Настоящие deep-триггеры:

- клиентские данные;
- роли и права;
- интеграции с почтой, мессенджерами и CRM;
- audit trail;
- AI-рекомендации;
- explainability;
- privacy boundaries.

Что сработало:

- `deep` выбран правильно;
- методология заставила увидеть данные, доступы, trust и интеграции как основу проекта;
- новое окно Codex получает короткий маршрут чтения;
- AI не был описан как магический автономный агент.

Что мешало:

- стартовый контекст был слишком общим и сначала уводил в другой продукт;
- для AI-проектов нужна более явная рамка `MVP vs later`;
- нужен более явный deep-шаблон для `PROJECT_STATE.md`.

## Общий вывод волны

`deep` работает заметно лучше после правок `lite` и `standard`.

Все три тяжёлых проекта получили `deep` по настоящим причинам, а не потому что "проект большой".

Главная оставшаяся проблема: `deep` нужно не только включать, но и удерживать. Он должен создавать короткую карту рисков и MVP, а не превращать проект в библиотеку на будущее.

## Что стало ясно

- `deep` должен включаться по риску, данным, ролям, деньгам, интеграциям, файлам, trust/security, multi-party или AI-рискам.
- Для `deep` нужен отдельный формат `PROJECT_STATE.md`: не просто "ключевые файлы", а зоны входа по scope, data, roles, integrations, trust/security.
- Для AI и marketplace особенно нужен блок `MVP vs later`.
- Агентская изоляция всё ещё не идеальна: один агент снова записал AI CRM-контекст в основной starter, несмотря на запрет. Это надо считать обязательным post-check после каждого тестового агента.

## Рекомендация перед финальной правкой

1. Добавить deep-версию `PROJECT_STATE.md`: scope, data, roles, integrations, trust/security, next implementation step.
2. Добавить в AUTOPILOT правило `Deep не равен большой библиотеке`.
3. Добавить обязательный блок `MVP vs later` для `deep`.
4. Усилить правило тестовой изоляции: после каждого агента проверять корень на загрязнение.
5. Сохранить текущую маршрутизацию нового окна: `AGENTS.md` -> `PROJECT_STATE.md` -> `.business/INDEX.md` -> нужная зона.

## Текущая оценка AUTOPILOT после волны 3

Для тяжёлых проектов: 8.8/10 по агентам.

Моя оценка: 9/10.

Почему хорошо: выбор `deep` стал обоснованным, и Codex получает реальное понимание сложного проекта.

Почему не 10: deep ещё нужно сильнее защищать от распухания и дать отдельный короткий вход для сложных проектов.
