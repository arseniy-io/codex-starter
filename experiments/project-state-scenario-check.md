# Проверка PROJECT_STATE на сценариях lite / standard / deep

Дата: 2026-06-18

## Цель

Проверить, помогает ли `PROJECT_STATE.md` первой части AUTOPILOT экономить чтение после онбординга.

## Lite: одностраничный лендинг

Ожидаемое поведение:

- Codex читает `AGENTS.md`, `PROJECT_STATE.md`, один актуальный план и 2-3 файла из `.business/`.
- `ai-clone/` и `mastery/` не читаются без явной задачи про тон или метод.
- `PROJECT_STATE.md` не дублирует весь бизнес-контекст.

Оценка: работает.

Риск: если в `PROJECT_STATE.md` начать добавлять слишком много подробностей, он станет вторым `.business/INDEX.md`.

## Standard: обычный коммерческий сайт

Ожидаемое поведение:

- Codex видит текущий фокус и ближайший план.
- Для UX/текстов идет в `.business/INDEX.md`.
- Для стиля открывает только нужные файлы из `ai-clone/`.

Оценка: работает.

Риск: нужен короткий список ключевых файлов, иначе Codex может каждый раз заново выбирать из индекса.

## Deep: SaaS или продукт с ролями и данными

Ожидаемое поведение:

- Codex быстро видит, что перед задачами про роли, API, платежи, файлы, экспорт или интеграции нужно читать risk/trust файлы.
- Не читает всю `.business/`.
- Не путает MVP, roadmap и security boundaries.

Оценка: частично работает.

Пробел: в `templates/PROJECT_STATE.md.tmpl` нет отдельной секции для 2-5 ключевых файлов проекта. Для `deep`-проекта туда должны попадать, например, `roles-and-access.md`, `security-boundaries.md`, `mvp-scope.md`, `integrations.md`.

## Решение

Добавить в `PROJECT_STATE.md` и шаблон короткую секцию `Ключевые файлы проекта`.

Правило: это не список всей библиотеки, а 2-5 файлов, которые чаще всего защищают от неверных решений.
