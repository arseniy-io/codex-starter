# POST_AUTOPILOT - второй этап настройки Codex Starter

> Это продолжение после `AUTOPILOT.md`. Первый AUTOPILOT настраивает базовый проект. Этот файл добавляет второй уровень: личный контекст, методологии, правила обратной связи и опциональные интеграции.

## Правила для Codex

1. Иди по этапам сверху вниз и обновляй `last_completed_stage`.
2. Перед каждым этапом коротко объясняй, что будет создано и зачем.
3. Не дублируй то, что уже сделал `AUTOPILOT.md`: `.business/`, `plans/`, `retrospectives/`, базовый `AGENTS.md`, security hooks.
4. Не переноси инструкции из других инструментов без адаптации под Codex.
5. Если этап зависит от актуальной Codex-документации, сначала проверь docs. Если docs недоступны - остановись.
6. Не создавай большие библиотеки без правил чтения. У каждой новой папки должен быть `INDEX.md` или README.
7. Codex должен читать только нужные файлы под задачу, а не весь контекст целиком.
8. После финальной проверки обнови `completed: true` и `last_completed_stage: 8`.

## Этап 1. `ai-clone/`

Цель: создать личный контекст автора проекта: голос, принципы, стиль мышления, правила после ошибок.

Что сделать:

1. Проверь, есть ли `ai-clone/INDEX.md`. Если папки нет - создай минимальную структуру из starter-шаблона.
2. Объясни пользователю коротко: `ai-clone/` не заменяет `.business/`. `.business/` описывает проект, `ai-clone/` описывает автора решений.
3. Проведи интервью блоками:
   - `identity` - кто пользователь, что для него важно, куда он движется;
   - `voice` - как он говорит, какие слова любит и не любит;
   - `thinking` - как принимает решения;
   - `principles` - правила продукта, кода и бизнеса;
   - `style` - визуальные и текстовые предпочтения.
4. Задавай вопросы по одному. Если пользователь не знает ответ, предложи 2-3 варианта.
5. После каждого блока обновляй только нужные файлы в `ai-clone/`.
6. Не записывай чувствительные данные: паспорта, пароли, ключи, токены, полные `.env`.
7. В конце покажи дерево `ai-clone/` и назови 3-5 файлов, которые реально стоит читать в будущих задачах.

Проверка:

- [ ] `ai-clone/INDEX.md` есть и объясняет карту папки.
- [ ] В каждой подпапке есть README или содержательный файл.
- [ ] Нет личных секретов.
- [ ] Codex не обязан читать весь `ai-clone/` целиком.

## Этап 2. `mastery/`

Цель: создать папку методологий и экспертных подходов. Это не Codex skills, а справочный контекст для решений.

Что сделать:

1. Проверь, есть ли `mastery/INDEX.md`. Если папки нет - создай минимальную структуру из starter-шаблона.
2. Объясни пользователю коротко: `mastery/` - это не skills. Skills запускают workflow, `mastery/` даёт методы для мышления.
3. Выбери с пользователем одну область, которая чаще всего нужна проекту:
   - copywriting;
   - negotiations;
   - financial-analysis;
   - product-strategy;
   - decision-making;
   - другая область.
4. Создай папку `mastery/<area>/` и `mastery/<area>/INDEX.md`.
5. Добавь 1-3 метода только для выбранной области. Не создавай большую библиотеку "на будущее".
6. Каждый метод оформляй по структуре: источник, суть, когда применять, шаги, ограничения.
7. Если метод берётся из внешнего источника, используй проверяемые источники и не копируй большие фрагменты текста.
8. В конце обнови корневой `mastery/INDEX.md`.

Проверка:

- [ ] `mastery/INDEX.md` есть и объясняет карту папки.
- [ ] Есть только одна стартовая область.
- [ ] Каждый метод применим по шагам.
- [ ] Нет пересказов книг и длинных статей без алгоритма.
- [ ] `mastery/` не смешан с `.agents/skills/`.

## Этап 3. Усиление `AGENTS.md`

Цель: добавить в `AGENTS.md` маршрутизацию контекста: когда читать `.business/`, когда `ai-clone/`, когда `mastery/`.

Что сделать:

1. Открой `AGENTS.md` и проверь, есть ли там упоминания `.business/`, `ai-clone/` и `mastery/`.
2. Добавь короткий роутинг:
   - бизнес, продукт, UX, аудитория, цены - `.business/INDEX.md`;
   - голос, стиль, личные предпочтения, повторяющиеся ошибки - `ai-clone/INDEX.md`;
   - экспертный метод, фреймворк, анализ через подход автора - `mastery/INDEX.md`;
   - реализация фичи - `plans/`;
   - опыт прошлых сессий - `retrospectives/`.
3. Не заставляй Codex читать все папки в начале каждой задачи.
4. Оставь правило: сначала индекс, потом только 1-3 нужных файла.
5. Проверь, что `AGENTS.md` остаётся коротким и понятным.

Проверка:

- [ ] В `AGENTS.md` есть маршрутизация контекста.
- [ ] Нет правила читать весь `ai-clone/`, `mastery/` или `.business/` целиком.
- [ ] Новые папки не конфликтуют с `plans/` и `retrospectives/`.

## Этап 4. Feedback loop

Цель: связать ошибки, ретро и `ai-clone/feedback/`, чтобы повторяющиеся замечания превращались в короткие правила.

Что сделать:

1. Проверь, что есть `retrospectives/README.md`, `retrospectives/TEMPLATE.md` и `ai-clone/feedback/README.md`.
2. Объясни пользователю разницу:
   - `retrospectives/` - что произошло в конкретной сессии;
   - `ai-clone/feedback/` - постоянные правила на будущее.
3. Добавь в ретро-шаблон короткий блок `Feedback rule`, если его ещё нет.
4. Если пользователь говорит "не так", "больше так не делай", "в следующий раз делай иначе" - предложи создать правило в `ai-clone/feedback/`.
5. Правило создавай только для повторяемых и важных вещей, не для каждой мелочи.
6. Формат правила: `Rule`, `Why`, `How to apply`.
7. После создания правила обнови `ai-clone/INDEX.md`, если появился новый важный файл.

Проверка:

- [ ] Ретро не обязательно для микрозадач.
- [ ] В ретро есть место для возможного feedback-rule.
- [ ] `ai-clone/feedback/README.md` объясняет формат правила.
- [ ] Постоянные правила не смешиваются с историей сессий.

## Этап 5. Контекст-инжиниринг

Цель: описать, как Codex выбирает только нужный контекст под задачу и не загружает всё подряд.

Что сделать:

1. Проверь, что в `AGENTS.md` есть правило: сначала читать индекс нужной зоны, потом 1-3 релевантных файла.
2. Объясни пользователю рабочие слои контекста:
   - `.business/` - проект, продукт, аудитория, экономика;
   - `ai-clone/` - автор, голос, стиль, устойчивые предпочтения;
   - `mastery/` - методологии и экспертные подходы;
   - `plans/` - текущее выполнение;
   - `retrospectives/` - опыт прошлых сессий.
3. Для каждой новой задачи выбирай минимальный набор файлов:
   - задача про продукт - `.business/INDEX.md` и 1-3 файла из `.business/`;
   - задача про текст/тон - `ai-clone/INDEX.md` и нужные файлы из `voice/` или `style/`;
   - задача про подход/анализ - `mastery/INDEX.md` и нужную область;
   - продолжение реализации - актуальный план из `plans/`.
4. Если нужного файла нет - сначала скажи, какой контекст отсутствует, затем предложи создать его коротким интервью.
5. Не читай весь `ai-clone/`, `mastery/` или `.business/` без причины.

Проверка:

- [ ] В `AGENTS.md` есть правило минимального контекста.
- [ ] У каждой большой контекстной папки есть индекс.
- [ ] Codex умеет объяснить, почему выбрал конкретные файлы.

## Этап 6. Review-cycle

Цель: добавить лёгкий цикл проверки заметной фичи: ошибки, упущения, реальность проблемы, свежий взгляд, security review.

Что сделать:

1. Добавь в `AGENTS.md` или план задачи правило: заметная фича закрывается только после короткого review-cycle.
2. Review-cycle должен быть лёгким:
   - найти реальные ошибки в diff;
   - проверить упущенные edge cases;
   - сверить, что проблема реальна для проекта;
   - перечитать diff свежим взглядом;
   - провести security review, если есть данные пользователей, внешние API, платежи, файлы или отправка данных наружу.
3. Не запускай полный review-cycle для микрозадач и текстовых правок без риска.
4. Если проверка нашла проблему - исправь её и обнови план.
5. Если проверка дала правило на будущее - предложи записать его в `ai-clone/feedback/`.

Проверка:

- [ ] Review-cycle не обязателен для микрозадач.
- [ ] Для заметных фич есть проверка ошибок, edge cases и security.
- [ ] Найденные уроки могут перейти в `ai-clone/feedback/`.

## Этап 7. Skills, plugins, MCP

Цель: дать правила выбора и аудита Codex skills/plugins/MCP без установки лишнего.

Что сделать:

1. Объясни пользователю разницу:
   - skill - reusable workflow с `SKILL.md`;
   - plugin - installable bundle, который может включать skills, apps, MCP и hooks;
   - MCP - подключение к внешнему сервису или локальному серверу инструментов.
2. Ничего не устанавливай "на всякий случай".
3. Если workflow нужен только этому репозиторию - предпочитай repo-skill в `.agents/skills/`.
4. Если нужно распространять набор skills/apps/MCP/hooks - тогда рассматривай plugin.
5. Если нужен доступ к внешнему сервису или live-данным - рассматривай MCP.
6. Перед установкой или подключением проведи аудит:
   - источник и автор;
   - README и `SKILL.md` или `.codex-plugin/plugin.json`;
   - scripts, hooks, postinstall;
   - чтение `.env`;
   - внешние URL, `curl`, `wget`, `fetch`;
   - удаление или массовое перемещение файлов;
   - какие данные уходят наружу.
7. Для MCP проверь, какие env vars передаются серверу, какие tools включены и нужен ли allowlist.
8. После аудита дай вердикт: безопасно / подозрительно / опасно. Если подозрительно или опасно - не устанавливай.

Проверка:

- [ ] Нет глобальных установок без явной просьбы пользователя.
- [ ] Нет MCP "на всякий случай".
- [ ] Repo-skills лежат в `.agents/skills/`, а не в `.codex/`.
- [ ] Для каждого внешнего инструмента есть краткий аудит.
- [ ] Нет устаревших slash commands из исходной инструкции.

## Этап 8. Browser и automations

Цель: описать, когда использовать Browser/Chrome extension и когда создавать automations или scripts/cron.

Что сделать:

1. Объясни пользователю разницу:
   - in-app browser - для localhost, публичных страниц и визуальной проверки без Chrome-профиля;
   - Chrome extension - для задач, где нужен залогиненный Chrome: CRM, почта, внутренние панели;
   - automation - повторяющаяся задача по расписанию или heartbeat текущего thread.
2. Не подключай Chrome "на всякий случай". Сначала проверь, можно ли решить задачу in-app browser или обычным MCP/API.
3. Для Chrome extension:
   - предупреди, что сайты и история браузера могут быть чувствительным контекстом;
   - не включай always-allow без явной причины;
   - используй allowlist/blocklist осторожно;
   - не работай с секретами и платёжными действиями без присутствия пользователя.
4. Для automations:
   - сначала протестируй prompt вручную в обычном thread;
   - выбери thread automation, если нужен контекст текущего разговора;
   - выбери standalone/project automation, если каждый запуск независим;
   - для Git-репозиториев предпочитай worktree, если automation может менять файлы;
   - помни, что project-scoped automation требует включённую машину, запущенный Codex и доступную папку проекта.
5. Если задача лучше решается обычным cron/script без Codex - предложи этот путь.

Проверка:

- [ ] Chrome не подключён без реальной нужды.
- [ ] Automation prompt протестирован вручную.
- [ ] Режим доступа и sandbox понятны пользователю.
- [ ] Для file-changing automation выбран безопасный режим: worktree или явное согласие на local mode.
