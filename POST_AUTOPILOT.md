# POST_AUTOPILOT - второй этап настройки Codex Starter

> Это продолжение после `AUTOPILOT.md`. Первый AUTOPILOT настраивает базовый проект. Этот файл добавляет второй уровень: личный контекст, методологии, правила обратной связи и опциональные интеграции.

## Правила для Codex

1. Иди по этапам сверху вниз и обновляй `last_completed_stage`.
2. Перед каждым этапом коротко объясняй, что будет создано и зачем.
3. Не дублируй то, что уже сделал `AUTOPILOT.md`: `.business/`, `plans/`, `retrospectives/`, базовый `AGENTS.md`, security hooks.
4. Не переноси инструкции из других инструментов без адаптации под Codex.
5. Если этап зависит от актуальной Codex-документации, сначала проверь docs. Если docs недоступны - остановись.
6. Не создавай большие библиотеки без правил чтения. У каждой новой папки должен быть `INDEX.md` или README.
7. Codex должен читать только нужные файлы под задачу, а не весь контекст целиком.
8. Перед завершением обязательно пройди privacy-gate для `ai-clone/` и `mastery/`.
9. После финальной проверки обнови `completed: true` и `last_completed_stage: 8`.

## Этап 1. `ai-clone/`

Цель: создать личный контекст автора проекта: голос, принципы, стиль мышления, правила после ошибок.

Важно: `ai-clone/` почти всегда содержит личный контекст. Это не обязательно секреты, но это может быть приватная информация о человеке, целях, стиле мышления, слабых местах и предпочтениях.

Что сделать:

1. Проверь, есть ли `ai-clone/INDEX.md`. Если папки нет - создай минимальную структуру из starter-шаблона.
2. Объясни пользователю коротко: `ai-clone/` не заменяет `.business/`. `.business/` описывает проект, `ai-clone/` описывает автора решений.
3. Проведи интервью блоками:
   - `identity` - кто пользователь, что для него важно, куда он движется;
   - `voice` - как он говорит, какие слова любит и не любит;
   - `thinking` - как принимает решения;
   - `principles` - правила продукта, кода и бизнеса;
   - `style` - визуальные и текстовые предпочтения.
4. Задавай вопросы по одному. Если пользователь не знает ответ, предложи 2-3 варианта.
5. После каждого блока обновляй только нужные файлы в `ai-clone/`.
6. Не записывай чувствительные данные: паспорта, пароли, ключи, токены, полные `.env`.
7. В конце покажи дерево `ai-clone/` и назови 3-5 файлов, которые реально стоит читать в будущих задачах.

Проверка:

- [ ] `ai-clone/INDEX.md` есть и объясняет карту папки.
- [ ] В каждой подпапке есть README или содержательный файл.
- [ ] Нет личных секретов.
- [ ] Есть понимание, останется ли `ai-clone/` в git или будет снят с tracking на финальном privacy-gate.
- [ ] Codex не обязан читать весь `ai-clone/` целиком.

## Этап 2. `mastery/`

Цель: создать папку экспертных линз: методы признанных авторов, практиков и школ мышления по областям, которые реально нужны проекту. Это не Codex skills, а справочный контекст для решений.

Что сделать:

1. Проверь, есть ли `mastery/INDEX.md`. Если папки нет - создай минимальную структуру из starter-шаблона.
2. Объясни пользователю коротко: `mastery/` - это не skills. Skills запускают workflow, `mastery/` даёт экспертные методы для мышления.
3. Выбери с пользователем одну область, которая чаще всего нужна проекту:
   - copywriting;
   - negotiations;
   - financial-analysis;
   - product-strategy;
   - decision-making;
   - другая область.
4. Создай папку `mastery/<area>/` и `mastery/<area>/INDEX.md`.
5. Найди или вместе с пользователем выбери 3-5 признанных авторов, практиков или школ мышления в этой области. Для маленького проекта можно начать с 1-2, если пользователь явно хочет лёгкую версию.
6. По каждому автору выдели 1-3 сильных метода. Не пересказывай книгу целиком: нужен конкретный приём с алгоритмом "что делать, как делать, когда применять".
7. Создай по каждому автору отдельный файл `mastery/<area>/<author>.md`.
8. Каждый авторский файл оформляй по структуре:
   - кто автор и почему его методам можно доверять;
   - метод 1: название, суть, когда применять, шаги, ограничения;
   - метод 2: то же самое, если он реально нужен;
   - метод 3: только если без него файл заметно слабее;
   - связи с другими авторами или методами через викилинки `[[имя-файла]]`, если они помогают.
9. В `mastery/<area>/INDEX.md` добавь карту области: список авторов с одной строкой про каждого и подсказкой, когда читать файл.
10. Если метод берётся из внешнего источника, используй проверяемые источники и не копируй большие фрагменты текста.
11. Если работа идёт из транскрипта, положи сырой материал в `mastery/<area>/raw/`, а в авторский файл вынеси только короткую применимую выжимку.
12. В конце обнови корневой `mastery/INDEX.md`.

Проверка:

- [ ] `mastery/INDEX.md` есть и объясняет карту папки.
- [ ] Есть только одна стартовая область.
- [ ] Внутри области один файл = один автор, практик или школа мышления.
- [ ] В каждом авторском файле есть 1-3 метода, применимых по шагам.
- [ ] Нет пересказов книг и длинных статей без алгоритма.
- [ ] `mastery/` не смешан с `.agents/skills/`.

## Этап 4. Feedback loop

Цель: связать ошибки, ретро и `ai-clone/feedback/`, чтобы повторяющиеся замечания превращались в короткие правила.

Что сделать:

1. Проверь, что есть `retrospectives/README.md`, `retrospectives/TEMPLATE.md` и `ai-clone/feedback/README.md`.
2. Объясни пользователю разницу:
   - `retrospectives/` - что произошло в конкретной сессии;
   - `ai-clone/feedback/` - постоянные правила на будущее.
3. Добавь в ретро-шаблон короткий блок `Feedback rule`, если его ещё нет.
4. Если пользователь говорит "не так", "больше так не делай", "в следующий раз делай иначе" - предложи создать правило в `ai-clone/feedback/`.
5. Правило создавай только для повторяемых и важных вещей, не для каждой мелочи.
6. Формат правила: `Rule`, `Why`, `How to apply`.
7. После создания правила обнови `ai-clone/INDEX.md`, если появился новый важный файл.

Проверка:

- [ ] Ретро не обязательно для микрозадач.
- [ ] В ретро есть место для возможного feedback-rule.
- [ ] `ai-clone/feedback/README.md` объясняет формат правила.
- [ ] Постоянные правила не смешиваются с историей сессий.

|---|---|---|---|
| `PROJECT_STATE.md` | В начале нового окна и перед заметной задачей | После смены фокуса, следующего шага или ключевых файлов | Не превращать в подробный бизнес-документ |

| `mastery/` | Нужен метод, фреймворк, экспертный подход | Когда добавлен реально используемый авторский метод с шагами и ограничениями | Не собирать библиотеку "на будущее" |

| `retrospectives/` | Нужно понять прошлые решения или уроки | После заметной сессии | Не читать все ретро в начале задачи |
| `experiments/` | Нужны гипотезы, сравнения, stress tests | Когда эксперимент завершён или дал вывод | Не считать источником истины |

## Этап 8. Browser и automations

Цель: описать, когда использовать Browser/Chrome extension и когда создавать automations или scripts/cron.

Что сделать:

1. Объясни пользователю разницу:
   - in-app browser - для localhost, публичных страниц и визуальной проверки без Chrome-профиля;
   - Chrome extension - для задач, где нужен залогиненный Chrome: CRM, почта, внутренние панели;
   - automation - повторяющаяся задача по расписанию или heartbeat текущего thread.
2. Не подключай Chrome "на всякий случай". Сначала проверь, можно ли решить задачу in-app browser или обычным MCP/API.
3. Для Chrome extension:
   - предупреди, что сайты и история браузера могут быть чувствительным контекстом;
   - не включай always-allow без явной причины;
   - используй allowlist/blocklist осторожно;
   - не работай с секретами и платёжными действиями без присутствия пользователя.
4. Для automations:
   - сначала протестируй prompt вручную в обычном thread;
   - выбери thread automation, если нужен контекст текущего разговора;
   - выбери standalone/project automation, если каждый запуск независим;
   - для Git-репозиториев предпочитай worktree, если automation может менять файлы;
   - помни, что project-scoped automation требует включённую машину, запущенный Codex и доступную папку проекта.
5. Если задача лучше решается обычным cron/script без Codex - предложи этот путь.

Проверка:

- [ ] Chrome не подключён без реальной нужды.
- [ ] Automation prompt протестирован вручную.
- [ ] Режим доступа и sandbox понятны пользователю.
- [ ] Для file-changing automation выбран безопасный режим: worktree или явное согласие на local mode.

## Финальная проверка

### Privacy-gate

Объясни пользователю:

> «Сейчас проверим, что личный контекст и методологии не попадут туда, куда не должны. Security audit ищет секреты, но не решает за нас, можно ли коммитить личный профиль, цели, стиль мышления или материалы из внешних источников.»

Сначала покажи, какие файлы отслеживает git:

```bash
git ls-files ai-clone/* mastery/*
```

Если shell на Windows не принимает glob так же, используй PowerShell:

```powershell
git ls-files 'ai-clone/*' 'mastery/*'
```

Затем спроси решение по `ai-clone/`:

1. **Приватный repo, можно оставить tracked.** Подходит, если пользователь понимает риск и репозиторий не будет публичным.
2. **Снять с tracking и добавить в `.gitignore`.** Подходит, если там есть личные данные или репозиторий может стать публичным.
3. **Оставить только безопасную короткую версию.** Подходит, если Codex должен знать стиль работы, но без личных подробностей.
4. **Не решили.** Тогда не делай финальный commit и не отмечай privacy-gate как пройденный.

По `mastery/` проверь отдельно:

- нет длинных копий книг, курсов, статей и платных материалов;
- нет приватных данных клиентов;
- каждый авторский файл содержит короткие применимые методы, а не пересказ источника;
- понятно, когда Codex должен читать каждого автора.

Если пользователь решил снять папку с tracking, выполни только после подтверждения и только для выбранной папки.

Для `ai-clone/`:

Windows/PowerShell и macOS/Linux:

```bash
git rm -r --cached ai-clone/
```

Для `mastery/`:

Windows/PowerShell и macOS/Linux:

```bash
git rm -r --cached mastery/
```

Добавляй в `.gitignore` только те папки, которые пользователь решил не хранить в git.

Запиши решение во frontmatter:

```yaml
privacy_ai_clone: tracked_private|ignored|safe_summary_only|undecided
privacy_mastery: tracked|ignored|needs_review
```

Если `privacy_ai_clone: undecided` или `privacy_mastery: needs_review`, не ставь `completed: true`.

- [ ] Нет устаревших файлов, папок и команд из исходной инструкции под другой инструмент.
- [ ] Первый `AUTOPILOT.md` остался коротким.
- [ ] Новые папки имеют `INDEX.md` или README.
- [ ] В `AGENTS.md` есть понятный роутинг контекста.
- [ ] Если `ai-clone/` заполнен личными данными, решено: коммитить в приватный repo или добавить в `.gitignore` и снять с tracking.
- [ ] Если `mastery/` содержит материалы из внешних источников, там нет длинных копий copyrighted-текста.
- [ ] `git diff --check` проходит.
- [ ] Security audit проходит: `scripts/security-audit.ps1` на Windows или `scripts/security-audit.sh` на macOS/Linux.
