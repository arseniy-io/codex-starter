# Критика плана через 3 независимых ревью

**Когда брать:** когда Codex написал первый вариант плана в `plans/YYYY-MM-DD-название.md` и ты готов проверить его прежде чем начинать реализацию.
**Что делает:** смотрит на план с трёх сторон: техника, бизнес, UX. Если твоя поверхность Codex поддерживает параллельных агентов - можно запустить их параллельно; если нет - сделай три последовательных ревью.
**Результат:** улучшенный план с закрытыми дырами, которые ты бы не увидел один.

## Почему это работает

Один проход часто защищает собственный план. Три независимых угла зрения заставляют проверить технические риски, бизнес-цель и пользовательский сценарий до начала кода.

## Рабочий цикл

1. Codex пишет первичный план в `plans/YYYY-MM-DD-название.md`
2. Ты открываешь новый чат или отдельный проход ревью
3. Запускаешь промпт ниже
4. Возвращаешься к исходному плану и обновляешь с учётом критики
5. **Только после этого** - реализация

## Промпт

```prompt
У меня есть первичный план реализации: [путь к файлу, например plans/2026-04-23-payment-form.md].

Задача:
1. Прочитай план целиком.
2. Прочитай .business/INDEX.md и связанные файлы - чтобы понять контекст проекта.
3. Сделай 3 независимых ревью:
   - техническое: реализуемость каждой фазы, риски, зависимости, тесты
   - бизнес-ревью: соответствие целям из .business/, метрики, приоритет
   - UX-ревью: пользовательский сценарий, непонятные места, ошибки и пустые состояния
4. Собери их выводы в один отчёт с конкретными правками: что добавить, что убрать, что переформулировать.
5. Покажи мне отчёт. Я решу какие правки принять, и попрошу тебя обновить файл плана.

Всегда отвечай на русском.
```

## Что делать с отчётом

- **Критика обоснована** → обнови план
- **Критика промах** (агент не понял контекст) → отметь себе, пропусти
- **Критика поднимает новый вопрос** → не фикси сейчас, добавь в «Открытые вопросы» плана

## Правило

Не делай все правки разом. Пройдись по отчёту пункт за пунктом. На каждую правку принимай осознанное решение «да/нет/позже».
